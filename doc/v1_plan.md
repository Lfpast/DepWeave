# DepWeave：在有限上下文中保留跨文件依赖证据

## 研究主张

主问题按你最新的澄清界定为：**全局图导航与局部任务记忆结合后，能否让 Qwen3-4B 更准确地定位仓库实体，并识别它与其他文件中实体的真实依赖绑定？**“正确”要求给出可核对的实体身份和源码位置。

论文的候选贡献是**依赖证据在两层之间、以及多轮之间的保真传递**：局部记忆保存已核实的实体和关系，后续查询能沿同一身份回到仓库源码；未解析的调用和预算裁掉的关系明确留作缺口。

## 双层交互与实现

现状需要先说清：[globalMem 的图索引](/home/jackson/python/DepWeave/globalMem/pixelmem/v5/plugins/code_graph/index.py:73) 和 [localMem 的流水线](/home/jackson/python/DepWeave/localMem/core/pipeline.py:76) 目前各自运行；`reuse_index` 复用抽取结果，并没有保存跨轮任务证据。两边还各有名为 `pixelmem` 的包。实施时保留现有模块，用 globalMem 已有的 MCP 服务传递结构化证据，避免在同一进程混用两套导入路径。

- **globalMem 管仓库快照与导航。** 为定义和关系使用统一 ID：`快照 ID＋相对路径＋限定名＋定义行`。返回候选实体、带调用位置的 `calls/imports/inherits` 关系、解析状态及索引覆盖情况。修正当前仅凭“全仓同名唯一”就绑定裸调用的风险；保留多个调用位置，并显式报告未解析调用、解析失败和未索引文件。源码快照是核对依据，图只负责指出到哪里查。
- **localMem 管任务证据。** 利用现有函数描述、源码片段抽取与候选排序，先找候选，再请求 globalMem 展开相关路径。按“实体＋关系＋源码位置”成组选择证据，用 Qwen 的实际 tokenizer 控制完整输入预算；提示中分开呈现已核实关系与缺口。
- **跨轮保存。** 局部任务记忆记录所采用的证据 ID、来源、未解决项和快照 ID，不把模型自己的猜测写成已证实关系。下一轮复用证据；仓库快照变化时，先重新核对再使用。跨层接口固定为 `EvidencePacket(snapshot_id, coverage, candidates, edges, gaps)`，其中每条边包含两端实体 ID、关系类型、源码位置和解析状态。

## 验证设计

保留两项原生评测及其原始分数，同时增加能检验研究主张的指标：

- **RepoQA Python：**在现有 100 条函数定位任务上保留函数名准确率，另核对完整实体 ID。对样本逐一独立标注可判定的跨文件关系及源码位置；据此构造同仓库的连续查询，最后一轮检验先前找到的实体与关系能否被正确复用。衍生任务单列报告，不称为官方 RepoQA 分数。
- **DependEval Task 2：**保留现有 166 条、3–5 文件样本的官方顺序精确匹配；另从源码独立核验文件间约束，报告关系识别与违反约束的比例。多个合法拓扑顺序可能存在，因此一次 `wrong_order` 不自动算作依赖幻觉。[DependEval 论文](https://aclanthology.org/2025.findings-acl.373/)
- **同预算对照：**比较原有 localMem 卡片、globalMem 图导航、平铺源码片段、双层但不跨轮保存、完整双层方案。再分别去掉关系、源码位置和缺口标记。所有方法用同一 Qwen3-4B、仓库快照与候选范围；主输入上限 4096 token，2048/8192 token 做敏感性分析。
- **主要判据：**完整实体及跨文件绑定准确率；同时报告有源码支持的关系比例、错误绑定、拒答、跨轮重复犯错、输入 token 和索引成本。按仓库做配对置信区间。只有关系和跨轮消融支持增益，且提升不是靠增加拒答取得，才主张双层机制改善可靠性。

实现验证需覆盖重名函数、导入别名与重导出、无法解析的 `x.m()`、多处调用、预算裁剪和仓库更新。先冻结标注与评测协议，再调方法，避免用图自身的输出充当真值。

## 默认边界

首版只研究 Python 与 Qwen3-4B；RepoQA 负责大仓库定位，DependEval 负责局部依赖约束，衍生的连续查询检验两者之间的证据复用。结果只能支持**实体与依赖绑定的识别可靠性**，不能推出生成代码的功能正确性。投稿前还需复核新近相关工作；现阶段的新颖性是有明确对照和证伪条件的研究假设，无法预先保证“别人没有”。
