# DepWeave：跨文件查询与调用的研究定位


## 唯一主 RQ

> **如何在有限上下文下，提高小模型跨文件查询与调用的可靠性？**

**RQ 描述问题，不预置解决方案**
可靠性包括查询结果是否符合仓库事实，以及生成的调用是否引用正确实体并满足功能要求。
依赖幻觉是重点错误类型，不将所有逻辑错误、漏检、拒答或静态解析失败都归为幻觉。


研究对象就是**跨文件代码查询和调用**：找到并解释实际依赖，随后正确使用仓库 API.
“小模型”是受益对象与受控变量，“调用正确”最终需要功能测试，不能只用调用了参考函数或生成了相同名字代替。

## Motivation：仓库依赖需求与可用上下文之间的矛盾

跨文件查询和调用需要结合分散在不同文件中的函数定义、调用关系与使用约束。
我们关注小模型在有限推理资源/上下文预算下使用大型仓库的场景：完整仓库无法常驻输入，
而截断、片段检索和多轮压缩可能使任务需要的依赖证据缺失或彼此脱节。
**由此要研究的风险是：模型是否会用猜测补齐缺失关系，产生不符合仓库事实的查询或调用。**
这是待验证的因果解释，不是已经测出的结果。

可用于 introduction 的一手证据：

| 来源 | 可以支撑的句子 | 不可外推的结论 |
|---|---|---|
| [Lost in the Middle，TACL 2024](https://aclanthology.org/2024.tacl-1.9/) | 接受长输入不代表稳健利用所有位置的相关信息 | 不能证明我们的小模型因窗口短而发生依赖幻觉 |
| [Context Length Alone Hurts LLM Performance Despite Perfect Retrieval，Findings EMNLP 2025](https://aclanthology.org/2025.findings-emnlp.1264/) | 在该研究的任务与模型中，即使相关信息可被正确检索，长输入仍可能降低任务表现 | 性能下降不等于幻觉率上升；不是所有小模型的规模定律 |
| [LLM Hallucinations in Practical Code Generation，ISSTA 2025](https://arxiv.org/html/2409.20550v2) | §IV-A/IV-C 讨论仓库上下文冲突、依赖冲突及获取项目上下文的困难 | 不是本项目的实验观察，也未证明我们所提跨轮机制 |


### 应当验证的 observation，而非预写成事实

> 在相同可用源码和 token 预算下，跨轮上下文丢失函数绑定或依赖路径，是否比单纯少一些
> 语义描述更容易导致小模型查询错误、调用错误？显式保留这些关系能否减少错误？

直觉是：零散片段和自然语言经验仍要求模型重新完成消歧、跨文件连接和历史重建。
CodeGraph 可以把一部分结构分析外置，Quill 则应保存任务过程中已经取得的关系证据。
但“小模型重建能力更弱”“通用记忆在此任务上更差”都必须经对照验证。
**现在不能说“大部分 memory 对小模型不好用”。**

## Methodology：依赖保真的双层记忆

目标是在有限上下文中提供可追溯、可复用的任务依赖证据，而不是容纳更多未组织的代码。

- **全局 globalMem**：从仓库解析函数身份、依赖关系及源码定位，作为可按需查询的证据库。
- **局部 shortMem**：保存当前任务已取得的依赖证据、约束和未解决项，跨轮复用而非重新猜测。
- **两层之间的保真组织**：检索与压缩使用一致的符号身份和来源；保留所选依赖关系，
  显示未解析或预算裁剪造成的缺口。保真针对所保留证据，不声称保留全部仓库语义。

以上是方法目标；完整策略尚未实现/验证。不是仅给已有两个模块换名字。

## Mechanism：需要 observation 支持的作用机制

Observation 是观察到的现象；Mechanism 是对现象以及方法为何有效的解释。
下列三项目前均为机制假设，不得在 introduction 中写成已经得到的发现。

| 机制假设 | 需要观察到的现象 | 对应方法作用 |
|---|---|---|
| 证据缺失会诱发错误补全 | 减少任务相关依赖证据后，不存在的实体引用或错误调用绑定增加 | CodeGraph 提供源码支持的身份、签名和关系，减少无依据猜测 |
| 节点命中不等于关系理解 | 即使相关函数均出现，缺失连接关系的表示仍比关系明确的表示更易出错 | 在预算内保留依赖关系，而不只独立选择相似代码片段 |
| 跨轮遗忘会破坏已建立的依赖理解 | 后续轮次重复出现此前已消除的调用错误，且与依赖证据被裁剪相关 | Quill 复用已取得的依赖证据，减少重复重建与遗忘 |

检索漏掉证据与模型看见证据却未正确使用是不同问题，不能混成一个“上下文不足”。
一个函数存在但被错误使用，也需要依据签名、源码或测试判断；不因为解析器没有找到
某条边就自动判模型幻觉。未解析状态必须与真值上的不存在区分。
如果仅靠增加拒答降低幻觉，而正确完成率没有改善，不能称为可靠性提升。

## Introduction 的逻辑顺序与缺口边界

**大型仓库需要跨文件依赖知识 → 有限预算与长上下文利用困难 → 依赖证据缺失/脱节的风险
→ 小模型跨文件查询与调用可靠性的 RQ → 依赖保真的双层记忆 → 机制假设与待验证贡献。**

必须纠正“此前无人用代码依赖解决幻觉”的说法：
[MARIN（FSE 2025 Industry）](https://arxiv.org/html/2505.05057v2) 已用局部/全局依赖挖掘和
依赖约束解码缓解 API 幻觉，并包含 DeepSeek-Coder-1.3B；“依赖＋小模型＋降低幻觉”
这三个关键词组合本身也不能称为首次。该工作的局部/全局依赖层级不等于我们的会话/仓库
记忆层级，但这种区别本身仍不足以证明贡献。

我们的候选缺口应表述为：**在有限上下文和多轮任务中，如何让依赖证据在仓库记忆与
会话记忆之间保持可追溯、可复用，从而降低依赖幻觉并提高任务完成的正确性。**
这延续现有工程方向，不宣称整个问题无人研究；还须区别于 CodeMEM 的会话机制和
RepoDistill 的图检索压缩。新增论文在此用于约束动机/新颖性，本轮不调整 baseline 或 benchmark 清单。

## 当前代码究竟支持什么

以下为实际实现审查，不以模块名称或 docstring 代替行为。

| 环节 | 代码位置 | 已有能力 | 不能提前声称的能力 |
|---|---|---|---|
| 全局记忆 | `codegraph/store.py`，`GraphUpdateEngine` | SQLite 保存分层边、来源、快照；增量刷新 | 边唯一键不含调用点；不是完整逐调用点证据库 |
| 依赖解析 | `extractor/languages/python/call_resolver.py`，`extractor/emitter.py` | 处理部分别名、类型、继承与调用绑定；记录位置和解析方式 | 动态调用有未解析情形；同一四元组去重会折叠多个调用位置；confidence 非校准概率 |
| 图导航 | `CodeGraphIndex.ego_graph/trace_call_chain/find_dependencies` | 局部关系、有限深度调用链、文件依赖 | 调用链有路径/深度限制；文件依赖不等于函数调用；输出短名不是唯一标识 |
| 检索入口 | `retrieval.py:HybridCodeGraphRetriever` | 默认按原始名称、签名、源码做向量相似度检索 | 类名虽有 Hybrid，当前该路径不是图与向量联合检索 |
| 局部会话 | `agent.py:_record`，`session.py:SessionCard.render` | 记录焦点符号/文件，组装相关事实与候选 | 默认观察传入空 facts/inferences；SESSION EVIDENCE 是候选提示，不是完整持久推理轨迹 |
| 预算与压缩 | `tuner.py:_apply_budget`，`quill/agent/loop.py:_render_history` | 分层排序后逐条取前缀；历史按字符截尾 | 未按依赖路径成组保留；不是模型 tokenizer 精确预算；可能丢弃跨轮绑定 |
| 评测接入 | `interfaces/` | 若干任务专用适配器 | 不等于完整 CodeGraph+Quill agent 评测；各接口并未统一经过会话记忆 |

另一个必须保持的边界：MCP `session_card` 经过 MemoryTuner，默认 agent 的 `read_session`
走 SessionManager 卡片；两者不能混写为同一实现。MCP 有 `code_trace`，默认 agent 工具表
没有直接暴露 `trace_call_chain`。编辑和测试工具也需调用者提供实现。

本轮验证：解析、session、tuner、agent 四组相关单测 **104 passed**。
其中包含“正确报告无法解析”的测试；通过不等于解析全覆盖，更不等于 benchmark 提升。

## 必须正面处理的 novelty 重叠

| 最接近工作 | 已经覆盖什么 | 对我们的约束 |
|---|---|---|
| [CodeMEM，Findings ACL 2026](https://aclanthology.org/2026.findings-acl.834/) | 代码上下文记忆＋代码会话记忆，AST 引导筛选与遗忘检测 | “全局＋局部”“代码专用 memory”“AST 保留”都不能单独称新 |
| [RepoDistill，Findings ACL 2026](https://aclanthology.org/2026.findings-acl.217/) | 图检索（含多跳路径）、学习式压缩预算分配和策略优化 | “图＋多跳＋省 token”也不是新颖性；不能把它描述成纯片段检索 |
| [Hydra，FSE 2026](https://github.com/solis-team/Hydra) | 结构索引、依赖感知检索；已评估 1.5B/7B 代码模型 | “依赖检索帮助小模型”已有直接先例 |
| [CodexGraph，NAACL 2025](https://aclanthology.org/2025.naacl-long.7/) | 结构化代码图与交互式图查询 | 图导航工具本身不是贡献 |
| [Repository Memory，ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/hash/b4c06f095368497f3ac19422efef8133-Abstract-Conference.html) | 用仓库历史信息增强 LocAgent 的定位 | 仓库图＋外部记忆组合本身不足够 |
| [Structurally Aligned Subtask-Level Memory](https://arxiv.org/abs/2602.21611) | 以子任务结构对齐记忆复用，而非只存整段轨迹 | 不能把“结构化/细粒度会话记忆”泛称首次；要具体到程序依赖证据 |

对 CodeMEM 还核对了公开实现：`context_selector.py` 已处理 import alias/API 名称，
`codemem.py` 已按 namespace 组织会话。区别不能只是“我们也给函数命名”。
其该版本筛选主要依据 API 集合相交；会话保存代码、AST diff 和经验链接。
我们要比较的是**跨函数、跨轮的依赖证据在压缩后的完整表达与可追溯性**，而不是否认它有代码结构。

## 候选贡献：一个机制，不是三个组件的拼装

**将任务相关的函数依赖证据作为全局检索和局部会话压缩共同维护的单位。**

- 全局 CodeGraph 提供带源码定位的函数关系，检索起点来自合法可见的查询/代码，而不是答案。
- 局部 Quill 维护当前任务已经访问的依赖子图、关联约束及未解决项；会话卡是该状态的视图，
  不是与图身份脱节的另一份文字总结。
- 在预算不足时明确选择、保留或延后读取关系证据；展示的路径须有来源，缺口须显式标注。
  一个候选证据记录可包括 `(caller ID, callsite, callee ID, source anchor, resolution status)`。
  不能把静态猜测标为“已验证”；函数签名也不是完整 API 使用前置条件。

这需要补齐现有选择、序列化和记录链路；**当前代码尚未实现上述完整策略**。
只改短名为全名、接上一个 trace 工具、修复漏接 session，都属于必要工程修复，
不能靠这些修复本身宣称研究创新。新方法必须有明确的保留目标/约束和跨轮读写规则。

截至本次核查，值得检验的缺口是：**在固定小模型和上下文预算下，联合维护这种依赖证据，
是否比已有代码记忆、图检索压缩以及同图通用记忆更可靠。**
这是基于已核查近邻的研究假设，不是“全世界无人研究”的证明，也不是已经成立的 novelty。

## 最小证据链与否证条件

这不是完整实验实施方案，而是 RQ 不跑偏的验收边界。

| 要支持的结论 | 必须出现的比较 | 首选任务 |
|---|---|---|
| 解析能提供可信依赖 | 对 PyCG/JARVIS 的边准确性、覆盖和成本；单列 unresolved | SWARM-CG / JARVIS 数据 |
| 查询确实更可靠 | 固定输入预算，比文本检索与结构方法；检查回答依据，不只相关性 | LongCodeU DRA、SWE-QA |
| 跨文件调用确实更正确 | pass@1/功能测试＋依赖使用；允许不同但正确的实现 | RepoExec、DevEval、CoderEval |
| Quill 会话层有必要 | 同图＋原始历史、同图＋通用摘要/记忆、CodeMEM、完整方法 | CodeIF-Bench L2 的多轮仓库任务 |
| 收益来自依赖保留 | 固定候选/源码内容与近似等长表示，比独立边选取与路径单位；测错误绑定/路径丢失 | 原任务上的预注册分层与诊断，不能冒充新官方榜单 |
| 特别帮助小模型 | 同模型家族 0.5B/1.5B/3B，资源允许再加入 7B 对照；比较增益与规模的交互 | 同一任务集、同一协议；7B 不称 frontier 大模型 |

预算需计入检索、全局索引、记忆写入/压缩、全部模型与工具调用；同时报告在线 token/延迟
和离线成本。不得悄悄让大模型替小模型写高质量记忆而不记账。
同时保留两种比较：原生完整系统端到端结果，以及固定候选与同图的机制隔离实验；后者
不是对原论文的忠实复现，前者也不能独自证明因果机制。

生成任务必须在建图、摘要、嵌入之前遮蔽目标实现及隐藏测试；参考依赖只用于评估。
单轮样本拼接成多轮须另列派生协议，不能冒充官方多轮 benchmark。
预先按依赖深度、跨文件数、同名歧义和会话长度分层；不能根据获胜结果事后挑选子集。
失败输出计入分母，按仓库/会话聚类计算区间，不能把同仓库函数视为完全独立样本。

**应放弃或缩小当前贡献的条件**：同图＋通用会话记忆同样好；修复工程漏接后差距消失；
收益只来自多给源码/更多调用/更强记忆写入模型；仅单轮有效却声称解决跨轮记忆；
依赖指标改善但执行正确率无改善。这些结果不能重新包装成“仍然验证了原假设”。

## 向 PhD 的简短表述

> 我们研究有限上下文下小模型跨文件查询与调用的可靠性。已有研究指出长上下文利用困难，
> 也发现仓库上下文缺失与依赖幻觉问题。我们据此提出依赖保真的双层记忆：CodeGraph 提供
> 全局依赖证据，Quill 在任务过程中保留和复用这些证据。要验证的是，显式依赖组织与跨轮
> 保留能否减少无依据的函数引用和错误调用，而不是仅增加检索量。机制和规模效应尚待实验，
> 不把“首次研究代码幻觉”或“双层记忆本身”当作贡献。
